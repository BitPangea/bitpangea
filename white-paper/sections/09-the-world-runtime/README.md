## Section Role

Section IX explains how a persistent digital World can change without allowing operational systems to redefine the World beneath them.

BitPangea must support:

- structures being created;
- permissions being updated;
- services operating;
- content being added;
- institutions acting;
- Builders modifying what they are authorized to control;
- participants causing legitimate state transitions.

The architectural problem is:

> **How can BitPangea change without losing continuity?**

World Runtime exists to answer that problem.

---

## Spatial Truth and World State

The section preserves a critical distinction between:

### Spatial Truth

Answers questions such as:

- What World exists?
- Where is a canonical location?
- Which Parcel occupies a place?
- What territory belongs to that Parcel?
- Which spatial relationships remain fixed?

### World State

Answers:

> **What is true within the World now?**

Examples of changing World State may include:

- structures;
- services;
- access rules;
- published material;
- institutional authority;
- objects and their current conditions.

The distinction is:

> **Spatial truth tells us what and where the World is.**

> **World State tells us what is true within it now.**

This separation allows BitPangea to remain stable at deeper levels while becoming dynamic above them.

---

## Persistent World State

World State must survive the interaction that caused it.

A legitimate change should not disappear merely because:

- a user closes an application;
- a processing service restarts;
- a client disconnects.

The persistence requirement is:

> **What legitimately becomes true of the World must be capable of remaining true after the interaction that caused it has ended.**

Persistent state allows the World to accumulate consequence.

Without persistence, activity becomes temporary display rather than durable World change.

---

## Request ≠ Authorization ≠ Execution ≠ Result

World Runtime should not create authority simply because it can execute an operation.

The section preserves:

```text
request
≠
authorization
≠
execution
≠
result
```

### Request

An attempt to cause change.

### Authorization

Determines whether the requested change is permitted.

### Execution

Performs the permitted operation.

### Result

Becomes part of World State if the operation succeeds.

The concise responsibility relationship is:

> **Authority permits. Runtime changes. Provenance remembers.**

---

## Runtime Does Not Own Authority

Authorization belongs to appropriate authority systems, including **Identity / Rights / Control**.

Runtime may consume authorization.

Runtime does not thereby become the source of:

- rights;
- identity;
- Parcel truth;
- constitutional authority.

This boundary is essential to prevent operational convenience from becoming structural authority.

---

## Validation Before Change

A permitted operation must still be valid.

The section states that validation may eventually consider:

- actor authorization;
- target existence;
- request form;
- protection of canonical spatial truth;
- required dependencies;
- present-state transition validity;
- conflicts;
- invalid resulting World conditions.

The broader principle is:

> **A technically executable action is not automatically a legitimate World change.**

Runtime must preserve World integrity rather than merely process commands.

---

## Execution

Once an operation is both authorized and valid, Runtime executes the change.

Where canonical outcome requires determinism, equivalent legitimate operations should not yield contradictory canonical results across conforming implementations.

The section preserves the distinction:

```text
implementation may vary
```

while:

```text
canonical meaning must remain coherent
```

Execution therefore sits between architectural meaning and technical realization.

---

## Protocols and Services

World Runtime may use protocols and services.

The section distinguishes them from authority.

### Protocol

Defines how systems interact.

### Service

Provides a usable capability.

Neither automatically becomes a source of canonical authority.

A protocol may carry an authorized instruction without creating the right to issue it.

A service may process World truth without owning that truth.

BitPangea should therefore be able to replace:

- services;
- protocols;
- implementation mechanisms

without replacing the World.

---

## Integrity

A living World requires more than successful execution.

It requires coherent results.

The section identifies possible integrity concerns including:

- contradictory updates;
- partial operations;
- invalid state transitions;
- duplicated effects;
- unauthorized mutation;
- corruption;
- divergence among conforming systems.

The architectural requirement is:

> **Consequential World change must preserve coherent World State.**

When an operation has multiple dependent effects, the World should not be left in an ambiguous intermediate state.

---

## Recovery

Persistence does not mean failure is impossible.

The section explicitly recognizes that:

- software crashes;
- networks partition;
- hardware fails;
- services become unavailable;
- implementations contain bugs.

Continuity should therefore not be defined as the absence of failure.

It should include the ability to recover coherently.

The section rejects:

> **The World must never fail.**

and instead preserves:

> **The World must be capable of recovering without losing its identity.**

Recovery Architecture must eventually determine how to identify authoritative state after interruption, incomplete operations, conflict, corruption, and component replacement.

---

## Runtime and Provenance

World Runtime changes the present.

Persistence / Provenance preserves the path to the present.

The section states:

> **Runtime changes the present. Provenance preserves the path to the present.**

This distinction supports later:

- verification;
- accountability;
- historical preservation;
- correction;
- institutional memory.

A mature World should be able to answer both:

> **What is true now?**

and, where appropriate:

> **How did it become true?**

---

## One Operational World

BitPangea is intended to support one canonical operational World even if multiple conforming implementations participate in operating or experiencing it.

Different implementations may use:

- different programming languages;
- different databases;
- different service architectures;
- different optimization strategies;
- different interface layers.

But where one canonical meaning exists, conforming systems must preserve it.

The governing principle is:

> **One operational World. Many conforming implementations.**

This is not a commitment to one technical Architecture.

It is a commitment to continuity of meaning.

---

## Runtime Is Not the World

The section explicitly states that World Runtime is not:

- the World itself;
- the source of Parcel identity;
- the source of actor rights;
- the permanent memory of every event.

World Runtime is:

> **the governed operational architecture through which legitimate change becomes current World State**

The responsibility separation is:

> **Spatial truth establishes the persistent World.**

> **Authority determines what change is permitted.**

> **Runtime executes legitimate change.**

> **Persistence / Provenance preserves continuity and evidence.**

---

## Relationship to Identity / Rights / Control

The relationship is:

```text
Identity / Rights / Control
→ determines legitimate authority

World Runtime
→ executes permitted operations
```

Runtime must not create rights simply because it can execute an operation.

Authorization and execution remain distinct.

---

## Relationship to Persistence / Provenance

The relationship is:

```text
World Runtime
→ changes present World State

Persistence / Provenance
→ preserves continuity, lineage, and evidence
```

This allows operational systems to evolve without erasing the World’s ability to explain how current state came to exist.

---

## Relationship to Interoperability

Runtime semantics must remain strong enough that multiple conforming implementations cannot create contradictory canonical World State.

This supports the broader principle:

> **Implementation diversity should not become semantic diversity.**

Different technical systems may execute or represent operations differently so long as the same canonical meaning is preserved where conformance requires one answer.
