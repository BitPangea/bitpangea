# The Architecture

## The Structural Design Record of BitPangea

This directory contains the public index and supporting resources for **The Architecture**, the institutional record within **The Atlas** that preserves the enduring structural systems through which BitPangea is made viable.

The Architecture connects permanent spatial truth to the systems that define:

- place;
- Parcels;
- authority;
- continuity;
- compatibility;
- operation;
- experience.

Its central purpose is to preserve durable architectural meaning without confusing implementation, presentation, or technology with permanent World truth.

## Architecture Membership

The Architecture is an institutional catalog of **nine recognized Architecture domains**.

Membership means that a domain belongs within BitPangea’s enduring structural design record.

Membership does **not**, by itself, establish:

- constitutional status;
- implementation;
- maturity;
- working priority;
- presentation priority;
- dependency order.

The nine recognized domains are:

1. Foundational Survey Fabric
2. Spatial Ground
3. General Spatial Interpretation
4. Parcel Cadastre
5. Identity / Rights / Control
6. Persistence / Provenance
7. Interoperability
8. World Runtime
9. Experience Architecture

This is the current institutional catalog.

## Domain Status Model

The Architecture currently uses three standing status classes on this index.

### Established

The domain’s architectural responsibility and governing structure are sufficiently developed to function as an active architectural record.

### Provisional

The domain is recognized and its general responsibility and boundary are understood, while substantial internal Architecture remains unresolved.

### Reserved

BitPangea has determined that a distinct architectural responsibility requires a permanent institutional home, while its governing Architecture remains intentionally undeveloped.

Status and order remain independent.

## Architecture Boundary Rule

BitPangea’s Architecture contains demonstrated dependencies without becoming one universal linear stack.

Where a lower domain provides stable truth or capability to a dependent domain above it, the lower domain should do so without absorbing the higher domain’s:

- identity;
- meaning;
- rights;
- state;
- lifecycle;
- implementation;
- experience.

The governing rule is:

> **A lower Architecture domain may establish the constraints that higher domains must not violate, but it should not prescribe the internal responsibilities, organization, implementation, or lifecycle of a higher domain unless that dependency is irreducibly necessary to the lower domain itself.**

Working form:

> **Protect the boundary. Do not design the layer above from the layer below.**

---

## Reference Does Not Transfer Authority

A recurring Architecture principle is:

> **Reference does not transfer authority.**

Examples:

```text
Parcel service
→ may expose Parcel information

Parcel Cadastre
→ still owns Parcel truth
```

```text
Builder
→ may reference rights

Identity / Rights / Control
→ still owns governed authority relationships
```

```text
World Runtime
→ may consume canonical spatial truth

World Runtime
→ does not thereby own the Survey or Cadastre
```

Architectural references should preserve authority boundaries rather than erase them.

---

## Deep Permanence, Higher Freedom

The Atlas Working Principle is:

> **The deeper the layer, the more permanent it should be. The closer the layer is to the user, the more freedom it should have to evolve.**

This does not create one strict universal dependency chain.

It expresses a permanence gradient.

Deeper truth should be harder to redefine casually.

Higher systems should retain greater freedom to evolve.

---

## Extend Upward, Do Not Rewrite Downward

The Architecture preserves:

> **Extend upward. Do not rewrite downward.**

Higher Architecture should build upon established deeper truth.

It should not casually redefine that truth in order to simplify later systems.

This applies especially to:

- Survey;
- World-space;
- Parcel identity;
- rights;
- Runtime;
- Experience.

---

## Permanent Place Is Independent of Ownership

BitPangea’s architectural boundaries preserve the distinction between:

```text
canonical place
```

and:

```text
rights, ownership, possession, or control
```

A Parcel remains the same canonical Parcel when rights change.

Ownership does not create Parcel identity.

Runtime does not create Parcel identity.

Experience does not create Parcel identity.

---

## Canonical Spatial Truth Is Independent of Runtime

The canonical spatial truth of BitPangea must not depend upon whichever Runtime implementation happens to be active.

Runtime may use canonical spatial truth.

It does not own or redefine it.

The World must be able to replace operational systems without changing what a canonical place is.

---

## Runtime Is Independent of Any One Implementation

World Runtime, when developed, must not become synonymous with:

- one server;
- one codebase;
- one database;
- one protocol implementation;
- one service provider.

Its architectural responsibilities should remain stable while implementations remain replaceable where the Architecture permits.
