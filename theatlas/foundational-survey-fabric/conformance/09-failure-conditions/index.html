Conformance Section 09 · Conditions That Defeat Compatibility

The conformance conditions under which an implementation must be judged incompatible, nonconforming, indeterminate, or unable to support a claimed Foundational Survey Fabric capability.

Failure Conditions define when an implementation has not satisfied the governing Specification and Conformance rules. They make incompatibility explicit rather than allowing ambiguous or approximate behavior to be represented as acceptable canonical variation.

A conformance system is incomplete if it defines only success. It must also identify the behaviors that invalidate a compatibility claim, distinguish implementation defect from unsupported capability or specification ambiguity, and prevent noncanonical behavior from being mislabeled as authoritative Survey truth.

Conformance Principle A conformance claim is meaningful only if failure is defined.
09.1 · Canonical Result Mismatch

Different Authoritative Results Constitute Failure

If an implementation produces an authoritative canonical result that differs from the result required by the governing Specification or Reference Vectors for the same canonical input, the applicable conformance claim shall fail.

Implementation-specific preference, optimization, or tolerance shall not excuse disagreement in canonical truth.

09.2 · Invalid Acceptance

Invalid Input Must Not Be Treated as Canonical

An implementation shall fail the applicable conformance requirement if it accepts malformed, impossible, ambiguous, out-of-domain, or otherwise invalid input as authoritative canonical Survey truth.

Higher-layer convenience repair may exist only where it is explicitly separated from canonical validation.

09.3 · Valid Rejection

Required Canonical Input Must Not Be Rejected

An implementation shall fail conformance if it rejects a valid canonical reference, expression, operation, or serialization that the governing Specification requires it to support within the claimed conformance scope.

A compatible implementation must recognize the canonical truth it claims to implement.

09.4 · Noncanonical Normalization Failure

Equivalent Input Must Normalize Correctly

Where valid noncanonical representations are supported, failure to normalize them to the required canonical meaning and form shall constitute a conformance failure.

Normalization that changes spatial meaning is likewise a failure.

09.5 · Exactness Failure

Tolerance and Approximation Cannot Establish Canonical Truth

Use of tolerance-based equality, silent rounding, hidden snapping, unresolved floating approximation, or implementation-specific convergence to determine an authoritative result shall constitute conformance failure where exact canonical behavior is required.

Approximation may exist outside the canonical layer but shall not be mislabeled as foundational truth.

09.6 · Hidden-State Failure

Mutable Context Must Not Change Canonical Output

If cache history, database sequence, session context, random state, user identity, ownership, wall-clock time, or other hidden mutable conditions alter an authoritative result, the applicable conformance claim shall fail.

State may improve performance. It may not participate in spatial truth.

09.7 · Serialization Failure

Canonical Interchange Must Remain Reproducible

An implementation shall fail serialization conformance if it cannot emit, parse, normalize, or preserve the canonical interchange representation required by the governing Specification.

Silent precision loss, incompatible field interpretation, or alternate authoritative serialization also constitutes failure where one canonical form is required.

09.8 · Version Compatibility Failure

Compatible Evolution Must Not Change Place

A conformance claim shall fail if an implementation applies a supposedly compatible version in a manner that renumbers, relocates, reinterprets, or otherwise changes established canonical spatial meaning.

Unsupported versions shall be identified explicitly rather than guessed.

09.9 · Independence Failure

Canonical Truth Must Not Depend on Exclusive Access

An implementation shall fail the independent implementation requirement if authoritative results can be reproduced only through inaccessible software, proprietary services, private data, undocumented convention, or exclusive institutional knowledge.

Canonical meaning must remain derivable from the published governing materials.

09.10 · Incomplete Mandatory Core

Partial Core Support Is Not Full Conformance

Failure to satisfy any required Mandatory Core capability shall prevent an implementation from claiming full Foundational Survey Fabric compatibility.

Partial, experimental, or developmental implementation may be described accurately, but it shall not be represented as fully conforming.

09.11 · Nontermination or Unresolvable Result

Canonical Truth Must Be Reachable

An implementation shall fail the applicable conformance requirement if a valid finite canonical input cannot be resolved to completion where the Specification requires a deterministic authoritative result.

Indefinite convergence, unresolved ambiguity, or potentially nonterminating interpretation is incompatible with canonical conformance.

09.12 · Unsupported Capability

Unsupported Is Not the Same as Incorrect

An implementation may encounter an optional capability or extension it does not support. Where that capability is outside its declared conformance scope, unsupported behavior need not constitute failure of the Mandatory Core.

The implementation shall identify the unsupported capability clearly and shall not fabricate canonical behavior for it.

09.13 · Specification Ambiguity

Some Disagreement May Reveal a Defect in the Standard

If independent implementations reasonably produce different results because the governing Specification does not determine one authoritative answer, the issue shall be classified as a specification ambiguity rather than automatically assigning implementation fault.

The ambiguity must be resolved through the proper specification-governance process before a definitive conformance judgment can be made for the affected case.

09.14 · Conformance Claim Misrepresentation

An Implementation May Claim Only What It Proves

A declaration that exceeds the conformance classes, specification versions, operations, or capabilities actually demonstrated shall be invalid.

Conformance reporting must distinguish proven compatibility from unsupported, untested, experimental, or noncanonical behavior.

Established by Requirements

The requirements establish exact canonical truth, deterministic validity and normalization, rejection of ambiguity, no silent snapping, detectable precision loss, independent implementation, finite representation, hidden-state independence, termination, exact-or-invalid canonical states, a mandatory conformance core, and deliberate attempts to expose ambiguity or hidden dependency before acceptance.

Still Open in Conformance

The formal failure-code taxonomy, severity classes, test-case disposition rules, retest procedure, distinction among fail, unsupported, indeterminate, and specification-defect outcomes, remediation process, certification withdrawal rules, and machine-readable failure report format remain unresolved until the complete Conformance framework is defined.
