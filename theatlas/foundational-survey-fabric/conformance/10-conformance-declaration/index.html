Conformance Section 10 · Formal Compatibility Evidence

The formal record by which an implementation demonstrates, limits, and declares its compatibility with the Foundational Survey Fabric Specification.

Conformance Report / Conformance Declaration is the final evidentiary layer of Foundational Survey Fabric conformance. It records what implementation was tested, against which governing Specification profile, under which Conformance scope, with what fixtures and outcomes, and therefore what compatibility claim the evidence supports.

The integrated candidate core now makes a substantial portion of that evidence model concrete. Reports can now identify exact CRPC behavior, Point / Segment / SCPE validation, exact predicates, deterministic normalization, ECEM precision semantics, FSF-CJSON-1.0 interchange, version scope, failure outcomes, and independent reproducibility evidence.

A Conformance Declaration remains the outcome of evidence, not a substitute for it. Neither the report nor the declaration canonically adopts the governing Specification or creates authority over the spatial truth that Specification defines.

Conformance Question How does software prove that it correctly implements the Specification?
10.0 · Integrated Conformance Standing

The Evidence Model Is Now Concrete Enough for Candidate Reports

Conformance Sections 01–09 now define a candidate proof surface covering Mandatory Core scope, result equivalence, validation, exactness, serialization, version compatibility, independent implementation, and failure conditions.

A candidate Conformance Report can therefore preserve meaningful executable evidence now, even though the final report schema, final machine-readable declaration schema, formal status identifiers, and canonical adoption process remain open.

10.1 · Purpose of the Conformance Report

Preserve the Evidence Behind the Claim

A Conformance Report shall preserve the evidence necessary to evaluate whether an implementation satisfies the applicable Foundational Survey Fabric Conformance requirements.

The report shall identify the tested implementation, governing Specification profile or compatibility identity, claimed Conformance scope, applicable normative encoding, test corpus, Reference Vectors or equivalent fixtures, observed results, failures, unsupported capabilities, ambiguities, and other evidence required by the governing framework.

10.2 · Purpose of the Conformance Declaration

State Only What the Evidence Supports

A Conformance Declaration shall summarize the compatibility claim established by the completed Conformance Report.

It shall not claim broader compatibility than the evidence supports and shall identify the governing Specification or compatibility identity, claimed profile, applicable serialization identity, result standing, and any material limitations.

10.3 · Implementation Identity

The Tested Software Must Be Identifiable

The report shall identify the implementation with enough precision to distinguish the tested artifact from materially different builds, configurations, forks, releases, or execution packages.

Candidate identity evidence may include implementation name, release identifier, source revision, build identifier, artifact digest, environment summary, or equivalent reproducible identifiers.

The final required identity fields remain open.

10.4 · Governing Specification and Profile Identity

The Standard Under Test Must Be Explicit

Every report shall identify the governing Foundational Survey Fabric Specification version or compatibility identity available at that stage and the Conformance profile against which the implementation was evaluated.

A declaration without a defined governing baseline shall not constitute a complete compatibility claim.

Final top-level FSF Specification identifier syntax remains open and shall not be invented by the report.

10.5 · Mandatory Core Scope

The Report Must Identify the Required Proof Surface

A report claiming current candidate Mandatory Core compatibility shall identify the applicable solved capabilities evaluated, including CRPC, canonical frame behavior, Point / Segment / SCPE validation, exact core predicates, deterministic normalization, ECEM precision semantics, and FSF-CJSON-1.0 where serialization compatibility is claimed.

Partial support shall be reported as partial support rather than implied as full Mandatory Core Conformance.

10.6 · Optional and Open Capability Scope

Untested, Unsupported, Experimental, and Open Behavior Must Remain Separate

The report shall distinguish successfully demonstrated optional capabilities from unsupported, untested, experimental, or Specification-open behavior.

Open mathematical gates shall not be presented as conformant merely because an implementation offers experimental behavior.

10.7 · Test Run Identity

Evidence Must Be Bound to a Specific Execution

Each formal test execution should carry a distinct test-run identity sufficient to connect the implementation artifact, governing profile, fixture set, evaluator or execution environment, date or sequence metadata where appropriate, and observed results.

The final test-run identifier syntax remains open, but reports shall not collapse materially different executions into one indistinguishable evidence record.

10.8 · Reference Vector and Fixture Record

Canonical Expectations Must Be Traceable

The report shall record the applicable Reference Vectors or equivalent executable fixtures used to establish the claimed result.

For each applicable case, the evidence should preserve the fixture identity, governing profile, expected authoritative result, observed result, and disposition.

Reports shall not imply execution of vectors or fixtures that do not yet formally exist.

10.9 · Validation Evidence

Input Classification Must Be Recorded Where Material

Candidate reports should preserve evidence demonstrating the required distinction among canonical-valid, valid-noncanonical, invalid, and explicitly unsupported behavior where the applicable profile uses those categories.

Where normalization is required, the report should preserve both the input identity and resulting canonical normalized output.

10.10 · Exactness and Result-Equivalence Evidence

The Report Must Show Exact Agreement Where Exactness Is Required

Evidence shall preserve exact expected and observed results for governed CRPC behavior, exact predicates, canonical normalization, exact supported measurements, and other Mandatory Core outputs.

Approximate decimal summaries may assist human review, but shall not substitute for exact evidence where the Specification defines exact canonical truth.

10.11 · Serialization Evidence

FSF-CJSON-1.0 Claims Require Canonical Byte Proof

A report claiming FSF-CJSON-1.0 compatibility shall preserve evidence sufficient to verify parsing, normalization-before-serialization, canonical structured CRPC representation, required object ordering, duplicate-key rejection, governed unknown-field handling, round-trip behavior, and canonical byte identity.

Where exact canonical bytes are required, the report shall preserve or reproducibly identify those bytes rather than only a human-readable rendering.

10.12 · Result Classification

Different Outcomes Must Remain Distinguishable

Each applicable test shall receive a deterministic disposition defined by the governing Conformance framework.

Candidate disposition concepts presently include: PASS, FAIL, UNSUPPORTED, INDETERMINATE, SPECIFICATION AMBIGUITY, and TEST / FIXTURE DEFECT.

These are candidate concepts, not yet final machine-readable canonical status identifiers.

10.13 · Failure Disclosure

Failures Must Remain Visible

A Conformance Report shall preserve all material failures, mismatches, unresolved ambiguities, unsupported mandatory capabilities, fixture defects, and other evidence that materially affects the claim.

A Conformance Declaration shall not omit known evidence that invalidates or materially limits the compatibility claim.

10.14 · Retest and Supersession Record

Later Success Must Not Erase Earlier Evidence

Where an implementation is corrected and retested, the later result may supersede the earlier claim for current standing, but the evidence model should preserve the distinction between the original failed run and the later successful run.

The formal retest, withdrawal, supersession, and evidence-retention procedures remain open.

10.15 · Independent Reproducibility Evidence

The Claim Must Be Verifiable by Others

The report should preserve enough information for an independent evaluator to reproduce the applicable tests and confirm the claimed result from the same governing materials.

Where independent implementation evidence is required, the report shall identify the independent implementation or implementations, their relevant identity, and the comparison evidence used.

10.16 · Conformance Declaration Integrity

The Claim Must Not Exceed the Proof

A Conformance Declaration shall be invalid if it claims compatibility beyond the tested Specification profile, demonstrated Conformance scope, normative encoding, tested operation set, or successfully completed Mandatory Core requirements.

The declaration shall accurately represent the boundaries of proven compatibility.

10.17 · Report and Declaration Versioning

Evidence Must Remain Bound to What Was Tested

Reports and declarations shall carry sufficient identity information to determine the implementation artifact, governing Specification/profile, applicable serialization identity, test corpus, Conformance rules, and test execution that produced the result.

A later implementation release, Specification revision, profile change, or serialization revision shall not automatically inherit an earlier declaration without whatever reevaluation the governing framework requires.

10.18 · Provenance and Authenticity

The Record May Be Verified Without Becoming Spatial Truth

Conformance Reports and Declarations may use signatures, hashes, publication records, provenance systems, content-addressed evidence, or other integrity mechanisms.

Such mechanisms authenticate the evidence record. They do not define canonical spatial meaning, canonically adopt the Specification, or grant amendment or succession authority.

10.19 · Candidate Machine-Readable Declaration Model

Conformance Should Be Interoperably Expressible

The completed Conformance framework should support a deterministic machine-readable Conformance Declaration containing the identities and outcome information necessary for software, registries, validators, or future infrastructure to evaluate the claim consistently.

Candidate content includes implementation identity, governing Specification/profile identity, serialization identity, claimed class/profile, test-run identity, overall standing, limitations, evidence references, and declaration provenance.

The final schema, encoding, required fields, status vocabulary, and interchange rules remain open.

10.20 · Human-Readable Declaration

The Claim Must Also Be Understandable

Conformance shall also be expressible in a concise human-readable form identifying what was tested, against what governing profile, for which scope, using which applicable serialization, with what overall result and limitations.

Human-readable summaries shall remain faithful to the underlying machine-verifiable evidence.

10.21 · Reassessment Boundary

Material Change May Require New Proof

Material changes to implementation behavior, governing Specification/profile, normative serialization, Conformance scope, Mandatory Core requirements, or relevant test corpus may require renewed evaluation.

The exact reassessment triggers remain open, but a declaration shall not be treated as timeless evidence for software or rules materially different from what was tested.

10.22 · Candidate Declaration Standing

Proof Produces the Claim

An implementation may make a candidate Foundational Survey Fabric compatibility claim only after satisfying the applicable Mandatory Core, all requirements of each claimed Conformance scope, validation and exactness rules, serialization obligations, version-compatibility requirements, independent implementation obligations where required, and applicable failure conditions.

The declaration is therefore the outcome of the Conformance framework—not an assertion that precedes it, and not a source of canonical authority beyond the compatibility scope actually proven.

Candidate Evidence Model Now Concrete

Implementation identity; governing profile; Mandatory Core scope; FSF-CJSON-1.0 scope; test-run identity; Reference Vector/fixture traceability; validity evidence; exact-result evidence; canonical-byte evidence; failure disclosure; independent reproducibility; retest/supersession history; declaration limits.

Still Open in Conformance

Final report schema; final machine-readable declaration schema; canonical status vocabulary; evaluator identity rules; evidence-retention policy; certification or registry role if separately authorized; signing/provenance mechanism; formal test-run identifier syntax; reassessment triggers; publication process; and final declaration lifecycle rules.

Conformance Integration Standing

The Final Evidence Layer Is Ready for Candidate Design, Not Canonical Issuance

The original section correctly established that proof must precede declaration. The integrated candidate Conformance model now provides enough structure to define a meaningful evidence record for the solved core.

Final schemas, status identifiers, certification mechanics, declaration lifecycle, and canonical adoption remain open. Conformance evidence can now be structured; canonical standing still belongs to the valid BitPangea adoption process.
