Conformance Section 04 · Canonical Input Classification

The conformance rules for how implementations classify, accept, normalize, or reject canonical and noncanonical Survey expressions.

Validation Behavior defines the required canonical judgment an implementation must make when presented with a Survey reference, extent, refinement expression, serialization, or other foundational spatial input.

Conforming software must distinguish valid canonical input from valid but noncanonical representation, malformed expression, out-of-domain reference, impossible refinement, ambiguous input, and other invalid states without relying on guesswork or silently inventing spatial meaning.

Conformance Principle Canonicalize what is equivalent. Reject what is not valid.
04.1 · Canonical Valid Input

Accept Authoritative Form

An input that satisfies the governing Specification and is already expressed in required canonical form shall be accepted as canonical Survey input.

Its spatial meaning shall be interpreted exactly and without modification.

04.2 · Valid Noncanonical Representation

Normalize Equivalent Meaning

A valid input that represents legitimate canonical spatial meaning but is not expressed in canonical form may be accepted where the Specification permits such representations.

The implementation shall deterministically normalize that input to the same authoritative canonical meaning and form required by the Specification.

04.3 · Malformed Expression

Reject Invalid Structure

An expression that violates the required grammar, serialization structure, field rules, refinement syntax, or other formal construction requirements shall be rejected as malformed.

A conforming implementation shall not infer intended spatial meaning from structurally invalid input.

04.4 · Out-of-Domain Reference

Reject Reference Beyond the Survey Domain

A mathematically structured reference that resolves outside the valid canonical Survey Domain shall fail validation as a BitPangea Survey reference.

It shall not be reinterpreted as Exterior, neighboring territory, alternate World-space, or another spatial category merely because its syntax can be parsed.

04.5 · Impossible Refinement

Reject Invalid Precision Structure

A refinement expression that violates the canonical refinement mathematics, uses an impossible branch or depth state, or otherwise cannot resolve under the Specification shall be rejected.

Implementations shall not repair impossible refinement through silent truncation, substitution, or snapping.

04.6 · Ambiguous Input

Do Not Guess Canonical Meaning

An input that permits more than one possible canonical interpretation under the applicable rules shall not be accepted as authoritative Survey truth.

Ambiguity shall result in deterministic validation failure unless the governing Specification defines an exact normalization rule that resolves it without changing spatial meaning.

04.7 · Approximate or Estimated Input

Approximation Is Not Canonical Truth

Estimated, rounded, approximate, pending, disputed, or incomplete spatial values shall not be accepted as canonical Survey truth unless they resolve exactly to a valid canonical representation.

Higher layers may preserve such states for their own purposes, but the Foundational Survey Fabric shall classify them separately from authoritative canonical input.

04.8 · Noncanonical Precision Reduction

Detect Loss Rather Than Hide It

Inputs produced through truncation, generalization, reduced storage precision, or lossy conversion shall be recognized as reduced representations where precision has been discarded.

Such inputs shall not be treated as fully equivalent to the original canonical expression unless the transformation is demonstrably lossless.

04.9 · Canonicalization Boundary

Normalization Must Preserve Place

Validation may normalize equivalent forms, canonical ordering, serialization, or representational syntax only where the resulting expression preserves identical canonical spatial meaning.

Validation shall not relocate a position, alter an extent, change refinement meaning, or substitute a nearby representable value.

04.10 · Deterministic Validation Result

The Same Input Receives the Same Judgment

Independent conforming implementations shall reach the same validation classification for the same input under the same Specification.

Validation behavior shall therefore be reproducible and implementation-independent.

04.11 · Failure Classification

Reject for Defined Reasons

The Conformance framework shall ultimately define deterministic failure classes sufficient to distinguish malformed syntax, invalid canonical structure, out-of-domain reference, impossible refinement, ambiguity, unsupported version, and other relevant validation failures.

Human-readable error wording may vary, but the canonical failure condition shall not.

04.12 · No Hidden Repair

Invalid Input Must Not Be Silently Corrected

A conforming implementation shall not silently repair invalid canonical input through snapping, rounding, truncation, inferred defaults, guessed intent, or implementation-specific fallback behavior.

Any higher-layer convenience feature that proposes a correction must remain explicitly separate from canonical validation.

Established by Requirements

The requirements establish deterministic validity and normalization; exact canonicalization; rejection of malformed or ambiguous input; exact addressability within the Survey Domain; no silent snapping; detectable precision loss; exact-or-invalid canonical states; hidden-state independence; and implementation-independent authoritative behavior.

Still Open in Conformance

The formal validation status codes, machine-readable error taxonomy, exact parser behavior, version-mismatch handling, distinction between recoverable and terminal validation failures, canonical diagnostics, and complete reference-vector set remain to be defined once the Specification is complete.
