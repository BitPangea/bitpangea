Reference Vector Section 01 · Canonical Address Resolution

The canonical test set for proving that independent implementations interpret, extend precision, normalize, and resolve Survey addresses identically without presuming one precision mechanism.

Addressing Vectors define exact executable cases proving that independent implementations interpret, normalize, compare, serialize, and preserve canonical Survey references identically.

The integrated candidate Specification now supplies a concrete addressing model for the capacity-independent core: exact reduced rational Pang coordinates (CRPC), canonical Point semantics, deterministic normalization, ECEM exact-place meaning, and FSF-CJSON-1.0 machine representation. Reference Vectors may therefore move from category-only planning into actual exact fixtures for those solved behaviors.

One upstream limit remains important: the numerical half-span of the Survey Domain is not yet canonically selected. Addressing Vectors may therefore use coordinates whose validity is independent of the eventual numerical Domain capacity, or symbolic/domain-relative cases where appropriate, but they shall not canonize a concrete Domain bound by example.

Reference Vector Question Given this exact input, what exact answer must every conforming implementation produce?
01.0 · Current Addressing Model

The Candidate Address Semantics Are Now Concrete

A canonical Survey Point is represented by an ordered pair (x, y) in the canonical frame, where each coordinate is an exact reduced rational Pang value.

q = n/d Pang, with n ∈ Z, d ∈ N+, gcd(|n|, d) = 1, and zero normalized as 0/1.

The canonical frame is +x = Panoris (East), -x = Panvel (West), +y = Pankor (North), and -y = Panvath (South).

Under ECEM, every valid canonical Point denotes one exact Survey position. It is not a cell, uncertainty region, parent reference, rounded location, or set of finer descendants.

01.1 · Basic Canonical Point Vectors

Exact References in the Canonical Frame

The vector set shall include exact canonical Points sufficient to prove that independent implementations interpret identical CRPC coordinate pairs as the same exact Survey position.

Capacity-independent fixtures should favor positions whose in-Domain validity does not depend upon the unresolved numerical half-span, including the canonical origin (0,0) and other coordinates that may be explicitly framed as conditional upon H where necessary.

01.2 · CRPC Normalization Vectors

Equivalent Rational Inputs Must Reduce Identically

The corpus shall include mathematically equivalent rational coordinate components expressed in nonreduced form where the input pathway permits them, together with the exact normalized CRPC result.

Examples shall prove sign normalization, denominator positivity, greatest-common-divisor reduction, and canonical zero representation without rounding or decimal approximation.

01.3 · ECEM Exact-Place Vectors

Greater Expressive Precision Must Not Move Place

Addressing Vectors shall demonstrate the ECEM rule that exact Points do not possess coarse and fine semantic states. A previously valid Point continues to denote the same exact place when future compatible Specification versions support additional exact coordinate values.

The corpus shall therefore test meaning preservation, not hierarchical refinement of an existing Point into descendants.

01.4 · Canonical Point Equality Vectors

Equal Coordinates Mean One Exact Place

Point equality shall be demonstrated through exact normalized CRPC component equality. Two supported Point representations denote the same canonical Point exactly when their normalized x-components are equal and their normalized y-components are equal.

No epsilon, tolerance, floating comparison, display precision, or rendering proximity may participate in canonical Point equality.

01.5 · Canonical Ordering Vectors

Deterministic Ordering Supports Canonical Geometry

The corpus shall include Point ordering cases sufficient to prove deterministic lexicographic ordering under exact CRPC comparison.

These vectors support later canonical Segment endpoint ordering, SCPE start-vertex selection, and other normalization rules that depend upon one implementation-independent Point order.

01.6 · Absolute Reference Vectors

Canonical Points Stand Without Higher-Layer Objects

Reference Vectors shall demonstrate that canonical Survey Points resolve independently of Parcels, Regions, landmarks, ownership, membership, or other higher-layer semantics.

The expected result shall be derivable solely from the canonical Point representation and governing Survey mathematics.

01.7 · Frame Interpretation Vectors

Coordinate Sign and Native Direction Must Agree

The corpus shall include exact cases demonstrating the canonical directional interpretation of coordinate sign.

+x Panoris · -x Panvel · +y Pankor · -y Panvath.

These vectors shall prove consistent interpretation of quadrants, axes, and the origin without assigning higher-layer geographic meaning.

01.8 · FSF-CJSON-1.0 Point Vectors

Canonical Meaning Must Survive Machine Interchange

Addressing Vectors shall include canonical FSF-CJSON-1.0 Point fixtures demonstrating structured CRPC components, canonical integer-string form, deterministic object-key order, UTF-8 canonical bytes, and exact parse/serialize round-trip behavior.

Where one canonical byte sequence is required, every conforming implementation shall produce the same bytes for the same normalized Point.

01.9 · Valid Noncanonical Input Vectors

Equivalent Input May Normalize; Invalid Input May Not Be Repaired

Where the implementation interface permits valid noncanonical rational or object representation, vectors shall demonstrate deterministic normalization to canonical CRPC and canonical Point form.

Invalid input shall remain invalid. Reference Vectors shall not use normalization as a mechanism for guessing, snapping, coercing, or silently repairing malformed or semantically invalid coordinates.

01.10 · Version-Preservation Vectors

Compatible Evolution Must Preserve Established Point Meaning

The corpus shall include compatibility cases proving that a Point valid under an earlier compatible Specification remains the same exact Survey position under a later compatible Specification.

Expansion of representational capacity may add newly expressible exact Points. It may not migrate, renumber, reinterpret, or reuse established Points.

01.11 · Domain-Boundary Dependency

Concrete Edge Cases Must Wait for the Numerical Domain Capacity

The candidate Survey Domain geometry is a closed axis-aligned square centered at the canonical origin and may be expressed parametrically as:

DH = {(x,y) : -H ≤ x ≤ H and -H ≤ y ≤ H}, with exact positive CRPC parameter H.

Because the numerical value of H remains unresolved, Reference Vectors shall not yet publish concrete canonical fixtures whose pass/fail status depends upon one specific numerical Domain edge.

Symbolic or parameterized Domain-boundary cases may document the intended rule, but final numerical edge fixtures require the governing Specification to select H.

01.12 · Addressing / Invalidity Boundary

Positive Addressing Cases and Negative Input Cases Remain Distinct

This section shall primarily establish exact valid Point meaning, normalization, equality, ordering, frame interpretation, serialization, and compatible meaning preservation.

Malformed CRPC, malformed Point structures, prohibited JSON forms, ambiguous input, and concrete out-of-Domain cases belong primarily in the dedicated Invalid-Input Vectors corpus, with cross-reference here where needed.

Executable Now

CRPC reduction and comparison; canonical zero; exact Point equality; Point ordering; frame interpretation; ECEM exact-place semantics; capacity-independent Point fixtures; FSF-CJSON-1.0 Point serialization; deterministic round-trip; compatible Point-meaning preservation.

Still Blocked or Open

Concrete numerical Domain-edge fixtures requiring a selected H; any alias system not defined by the Specification; future human-facing address syntax; unresolved higher geometry or operation cases outside Point addressing; final corpus identifiers and packaging.

Reference Vector Integration Standing

Addressing Has Moved From Category Planning to Exact Candidate Fixtures

The original page correctly refused to invent an address grammar before the mathematics existed. That condition has now changed for the capacity-independent core: CRPC, canonical Point semantics, ECEM, normalization, the canonical frame, and FSF-CJSON-1.0 provide enough exact behavior for real Reference Vectors.

The unresolved numerical Survey Domain capacity remains a real boundary. Reference Vectors may prove the rules around exact reference and Domain membership, but they may not choose the missing numerical half-span on the Specification's behalf.
